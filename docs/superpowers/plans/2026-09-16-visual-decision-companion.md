# 可视化需求解释与决策回传实施方案

> 已被 [通用人工介入交互层：调研与实施方案 v2](2026-09-16-human-interaction-layer-v2.md) 取代。用户明确要求覆盖各种 Agent 人工介入场景；下文保留为初稿，其中五条业务材料仅为示例，不再定义产品范围。选型、协议与验收以 v2 为准。

日期：2026-09-16。状态：提案，未实施。用户提供的五条倾向均未正式确认。

## 1. 目标与范围

把 Agent 给出的长篇需求、异常清单和技术取舍转换为可理解、可操作的 HTML；用户在手机或桌面逐项了解后提交选择，Agent 收到结构化结果并继续原任务。

成功标准：用户不需要理解数据库术语就能说明选择的实际后果；不用把页面答案复制回聊天；Agent 不会把建议、草稿或单次点击误当成最终决定。

本轮只产出实施方案。五条业务材料来自用户原文，未检查 gantt-task-editor 的实际数据库、迁移或测试，不能把材料中的实现断言视为本轮验证结果。

## 2. 当前依据

- 本地 `eli5/SKILL.md` 的核心指令是用 HTML artifact、大图和少量文字向零背景读者解释主题；文件没有结果回传协议。
- 本地 `brainstorming/visual-companion.md` 描述 HTML 页面、点击选项、写入 `state_dir/events` 的机制。当前技能目录只发现指令文档，没有其描述的启动脚本；尚未验证可运行的完整安装。
- 当前仓库 `src/cli.js` 有 start/capture/status/stop/doctor，以及 secret 子命令分发；没有 decision 命令。
- 当前 `src/secret-cli.js` 有 ask/wait/status 等表单生命周期代码，可作为交互模式参考。相关 secret 文件处于未提交开发状态，不能作为已验收依赖。
- `src/proxy.js`、`src/auth.js`、`src/tunnel.js` 提供现有预览基础设施。README 明确当前代理不转发 WebSocket，故第一版使用 HTTP 提交和本地结果读取，不依赖实时套接字。

## 3. 产品形态

建议增加独立的 `decision-companion` skill，第一版随 mobile-preview 插件分发。复用 ELI5 的解释原则；无需改写原 ELI5 skill，也不依赖 Superpowers 私有事件格式。

职责：

1. Skill：把上下文整理成解释、选项、证据、后果、疑点；生成结构化文档；启动会话；读取提交；将结果带回原任务。
2. 固定 HTML 渲染器：负责图示、选择、数字输入、补充意见、草稿和提交回执。
3. 决策运行时：负责会话隔离、输入校验、持久化、版本与重复提交处理、结果查询。
4. mobile-preview：负责手机可访问的认证预览链接与生命周期。

第一版不实现任意 HTML 执行平台、多用户协同、可视化流程编辑器或跨 Agent 平台的通用唤醒服务。

## 4. 用户流程

长文本 → 生成决策草案 → 打开 HTML → 看懂后果并调整 → 核对摘要 → 正式提交 → Agent 读取与确认 → 按既有任务授权继续。

首页：显示“5 个待决定的问题”，每项一行生活化标题、当前倾向和未解决问题。只有用户正式提交后才出现已提交标记。

详情每屏只处理一项：

- 一句话：现在要决定什么。
- 小图：两三个步骤或状态的变化，选不同方案时切换结果。
- 选项卡：能得到什么、会失去什么、还有什么不知道。
- “你的原始倾向”和“AI 建议”分开标注，均不计入确认进度。
- 原文与证据折叠显示，保留业务 ID 和出处。
- 提供数字输入、补充条件、暂缓、请求进一步解释/核实。

草稿可预填原始倾向，但必须显示“待确认”；批量确认也需经过汇总页，展示所有值和未解决条件。最终按钮为“提交这些决定”。

提交部分决定时，剩余项标记 deferred；涉及依赖的后续任务不能越过未决定项。提问产生 clarification_request，Agent 回答后生成新版草案，不伪装为已决策。

## 6. 内容与提交契约

采用版本化 JSON；浏览器只能提交白名单字段，不能提交可执行命令。

DecisionDocument：

- schemaVersion、documentId、revision、sourceDigest、title、context。
- sources：原文、出处、摘要哈希；无仓库证据的内容注明 user_provided。
- items：稳定 ID、通俗问题、术语解释、sourceRefs、options、consequences、unknowns、dependencies、userLeaning、agentRecommendation。
- 控件类型第一版限制为 single_choice、number、text、defer；图示采用 timeline、relationship、before_after 三种固定模板。
- optionId 稳定且不依赖顺序；参数有单位、校验约束和解释。017 分别保存 ttlMinutes 与 maxUnusedTokens。
- 决策表达分为 selected、conditional、deferred、needs_clarification，避免所有答案都压成一个选项字母。

Submission：

- sessionId、documentId、revision、sourceDigest、submissionId。
- answers：itemId、optionId、参数、conditions、comment、决策状态。
- confirmedItemIds：用户实际确认项，不接受浏览即确认。
- 客户端提供幂等键；服务端分配 receivedAt 与 receiptId。
- decisionScope 固定为本轮业务决策，不隐含新增部署、删除或执行命令授权；原任务已有授权继续有效。

服务端以其保存的文档校验答案；客户端不能通过替换 options、原文或推荐值改变提交语义。

## 7. 回传与状态管理

以下为拟新增命令，不是现有可运行命令：

```text
mp decision open --file decision.json --json
mp decision wait --id <session-id> --timeout 30 --json
mp decision result --id <session-id> --json
mp decision ack --id <session-id> --submission <submission-id> --json
mp decision close --id <session-id>
```

open 启动本地服务并复用认证预览链路，返回 sessionId、revision、expiresAt 和手机链接。wait 仅等待有限时长，超时返回 pending，超时不关闭会话、不代表用户同意。

页面用 HTTP POST 保存最终提交。服务端原子持久化后才返回成功回执；重复请求返回同一回执，不重复记录。并发的不同提交只接受首个，后来的请求返回冲突并展示已收结果。

业务状态：draft → submitted → acknowledged；草稿也可 cancelled。访问链接过期是独立状态，不删除已提交结果。Agent 必须读取、校验并接纳结果后再 ack，页面区分“已保存，等待 Agent”与“Agent 已接收”。

文档修改创建新 revision，旧页提交返回 stale_revision 并要求重新核对。最终提交不可原地覆盖；修改决定创建新修订并关联此前回执。

结果按会话存于本机应用状态目录，不进入仓库或普通日志；采用临时文件加原子替换，恢复时校验 schema 与校验和。已提交结果与 ack 均可在进程重启后读取。建议默认保留 7 天，可显式清理；页面草稿随该会话保存，需明确未提交。

## 8. Agent 怎么继续

正常路径：Agent 发出链接后，使用宿主支持的可中断等待或有界 wait 读取结果；pending 时可处理独立工作，再继续等待。收到提交后核对文档版本，将决定及条件带入原任务，然后 ack。

关键限制：文件或 HTTP 请求不会自然让一个已经结束回合的 Agent 重新运行。第一版必须实测当前 Happy/Agent 宿主如何保持等待或恢复任务，不能把“结果已写文件”宣传为“Agent 已自动继续”。

若宿主没有可用等待/事件机制，结果必须持续保存，页面显示“已保存，Agent 尚未读取”，用户回到聊天发一句“继续”即可读取，无需复制答案。全自动唤醒属于后续宿主适配，必须先验证其会话路由和授权接口。

提问也是事件：wait 可返回 clarification_request。Agent 解释后发布新版文档，迁移仍兼容的草稿答案；改动涉及的项需再次确认。

## 9. 实施批次

### P0：先证明闭环

用一条固定题目验证手机打开、提交、持久化、有界 wait、Agent ack，以及当前宿主的继续执行行为。检查预览反向代理对 POST 的透传和认证方式。产出可观察的提交回执与宿主能力结论，再冻结集成方案。

### P1：内容协议与解释规则

定义 JSON Schema、状态机和五条脱敏样例；新增 skill 的说明与输入输出契约。要求所有结论可追溯，原始倾向不自动确认，疑点不得在简化时丢失。对无效 ID、缺失单位、未支持控件、失效依赖等输入给出明确错误。

### P2：运行时与 CLI

新增 decision 专用服务、存储和命令模块；接入现有 `src/cli.js` 分发及 `src/usage.js` 帮助。认证、隧道模块先检查可复用接口，避免把未验收的 secret 实现变成硬依赖。

实现版本冲突、幂等提交、结果恢复、到期清理、ack 和澄清事件。浏览器草稿与最终提交分开存储。

### P3：HTML 交互

新增固定模板渲染器：概览、逐题详情、三种图示、数字字段、条件备注、原文折叠、提交摘要、回执。手机使用单列；桌面可以并排比较。支持键盘、清晰焦点、非颜色状态标记。

### P4：技能与插件接入

新增 decision-companion skill，明确“长文本理解/多个取舍/想在页面选择”触发条件。更新插件 README、必要的 manifest 和安装验证；不要默认凭增加目录就已完成宿主发现。仅在确认宿主接口后补自动事件适配。

### P5：端到端验收

使用五条原文跑完整流程，分别验证倾向预填、部分确认、条件选择、追问、刷新恢复、提交重试、旧版本拒绝和 Agent 回执。整理测试证据与局限，再考虑第二版任意解释图或更多宿主支持。

## 10. 必要验证与保护

- 内容验收：014 保留“AI 已采用”和“用户未确认”的差别；016 暴露引用完整性条件；018 演示根集合变化，不能误称永久稳定。
- 合同测试：非法选项、数值边界、未知字段、跨会话 ID、错误版本、条件与依赖校验。
- 状态测试：重复提交只生成一条结果；两个标签页冲突；落盘失败不能报成功；重启可读取；超时不确认；ack 可重试。
- 浏览器测试：改 017 两个数值、暂缓 016、提交其余项；刷新保留草稿；后退不能悄悄覆盖最终决定；页面显示服务端回执。
- 集成测试：真实手机提交后 Agent 得到完全相同的结构化结果；原会话恢复不会串到另一会话。
- 输入防护：文本转义、限制正文体积、拒绝脚本/外链注入；固定模板和 CSP。认证写接口检查来源与 CSRF，日志不输出预览 token 或整段私密材料。
- 第一版走普通认证预览，隧道提供方可能接触 HTML 与提交明文，不宣称端到端加密；密钥输入继续走专用 secret 流程。

## 11. 完成定义

用户能从这五条材料在手机完成理解、修改、部分提交或追问；Agent 可靠区分用户最终决定与原始倾向，收到稳定 ID、参数、条件、原文版本和回执；网络重试与进程重启不丢已提交结果。当前宿主是否支持无需用户追加聊天消息的继续执行，必须有实测结论。

第一版优先解决解释准确与回传可靠。视觉自由度和跨宿主自动唤醒在闭环被证明后扩展。
